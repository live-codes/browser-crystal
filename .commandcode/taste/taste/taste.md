# Taste
- Strongly favors client-side, no-server solutions: code should run entirely in the browser with no backend/remote server. Confidence: 0.7
- Prefers starting with a small, self-contained proof-of-concept (e.g. a simple HTML page) before building out a full integration. Confidence: 0.5
- Wants progress committed as checkpoints before continuing ("commit first then continue"), rather than leaving a pile of uncommitted work while moving on. Also approves committing at the end of a task when the agent offers ("yes" to "Want me to commit them?"), so work lands in the repo rather than sitting in the working tree. Confidence: 0.7
- Prefers the agent to keep driving a task to completion autonomously — e.g. continuing to poll/monitor long-running builds until they finish or fail — rather than stopping to check in at each step ("yes, continue"). Goes further on hard tasks: explicitly instructs the agent not to stop for interim progress reports and to only surface results once there is a working demo ("Keep iterating. Do not stop to show me progress till we have a working demo"). Confidence: 0.8
- Keeps all changes scoped to the current repo; treats sibling/dependency checkouts as read-only (e.g. "Keep all changes in this repo. Do not modify clang-wasm."). Confidence: 0.7
- Deliberately commits built artifacts into the repo (e.g. commenting out the gitignore entry for a ~140 MB build output) so a fresh clone needs no build step, accepting the repo-size cost. Confidence: 0.55
- Wants the proof-of-concept to be genuinely interactive, not a mock: user-editable code that actually compiles and runs in the page, rather than a read-only demo pane. Confidence: 0.55
- Expects the demo to support the full program input/output model, not a reduced subset — asks for whatever a real program needs to run (e.g. a stdin box so a program calling `gets` reads typed input), and expects parity with any reference/samples implementation that already has it. Confidence: 0.45
- Chooses the shortest path to a working result over build-from-source purity — happy to reuse another package's already-built assets (e.g. a sibling project's `lld` + memfs runtime) instead of cross-building the artifacts ourselves. Confidence: 0.5
- When a project hits a fundamental blocker, prefers fixing the root cause properly (accepting upstream-scale work) over workarounds or shipping a degraded/partially-disabled feature (e.g. chose "push on Crystal's codegen" over routing around exceptions or landing the page with compilation disabled; and when a mixed-EH module was rejected by V8, fixed it at the compiler-patch level with a second LLVM option rather than hunting for a workaround sysroot). Confidence: 0.55
- Wants reusable pieces of a project captured as thorough, standalone documentation — findings, build steps, and a reproducible pipeline — so others can reuse and reproduce it, not just the code. Confidence: 0.5
- Expects documentation to be maintained incrementally throughout a task, not written up at the end — keep adding detail to the README and a FINDINGS-style notes file as work progresses. Confidence: 0.65
- When a long task hits a wall or is handed off, wants a comprehensive, self-contained handoff document so a fresh session can start cold — goal, current state, environment/paths, exact next task, and the dead ends already ruled out. It is the operating mechanism, not an afterthought: work resumes by pointing the agent at the file ("read HANDOFF.md and continue"), so it must be detailed enough to drive the next session unaided. Confidence: 0.65
- Prefers to validate a package/module boundary against a real consumer before extracting it into a separate repo — e.g. chose "validate, then split": keep the reusable piece in place until a real downstream project links against it and proves its interface, then extract and publish it. Confidence: 0.45
- Minimizes runtime dependencies: prefers hand-written minimal implementations and vendoring third-party code into the repo (with its license files) over adding packages — e.g. a plain textarea instead of a syntax-highlighting library, a hand-written WASI host, and a vendored WASI shim so the page needs no `npm install`. Confidence: 0.5
- Structures core logic to be free of environment-specific APIs so the exact production code path can be driven from a fast headless harness (a Node script running the same modules against the same assets), instead of only being exercised through a real browser. Confidence: 0.45
s several concrete variants and compares them, and reports before/after numbers rather than guessing at the fix. Confidence: 0.5
- Values debuggability over squeezing out the last bit of size/latency — e.g. kept the wasm `name` section (declining `--strip-all`) because named stack traces are how the project debugs itself, when the further saving was marginal. Confidence: 0.45
- Cares about a lean shippable/loadable payload and will invest real effort reducing size once it works: apply post-link optimizers (e.g. `wasm-opt -Oz`), gzip everything and inflate client-side, and drop whole unused libraries/components (e.g. removing `libc++` and the compiler's own `compiler/` sources) rather than carrying them "just in case". Reports the before/after byte counts. Confidence: 0.5
- Prefers validating an optimization or generated artifact against the real target runtime (the authoritative consumer, e.g. V8/Node) before adopting it, rather than trusting a tool's own validator — Binaryen's validator accepted a module V8 rejected, so V8 is the check that settles it. Confidence: 0.4
- Cares about the developer's edit→run latency in the interactive tool, not just the shipped payload size: flags multi-second compile times as a problem worth fixing (e.g. "the compile times are quite long (~13-16s). Can we do anything to make this faster?"). Confidence: 0.5
- Judges a tool by its end-user-visible surface: the output pane should contain only what concerns the user — their program's output, warnings about their code, and build failures — with internal build chatter (tool-level link commands, known-benign linker warnings) suppressed. Calls out such noise the moment it appears ("Do we need to show the first 4 lines?"). Confidence: 0.7
- Prefers user-facing error text to be plain and meaningful instead of naming internal implementation artifacts — e.g. an internal-sounding "the compiler did not produce out.o.wasm" replaced by a "compilation failed" / "linking failed" heading over the real diagnostics. Confidence: 0.45
- Wants project-agnostic pieces pulled out of the application repo into their own standalone repository *and* npm package, so sibling/other projects can reuse them ("separate anything that is not specific to crystal compiler (e.g. libLLVM) into a separate repo. Make that available as npm package so that it can be reused for other compilers"). Reusability across similar projects is the goal, not just tidiness. Confidence: 0.6
- When a new package or library is created, wants it to mirror the conventions, option names and API shape of the established sibling packages in the ecosystem ("similar to `@live-codes/clang-wasm`", the nim-wasm package) rather than inventing a new interface. Confidence: 0.55
- Treats planning as collaborative: when asked to plan, expects the agent to contribute its own additional suggestions, risks and priorities on top of the list given, not just sequence the items ("Do you have any other suggestions or priorities?"). Confidence: 0.45
- Prefers to close out what is already known to be outstanding before starting new capability work — the first item of a plan is to finish whatever the handoff still lists as open and bring the docs in line with reality. Confidence: 0.45
- The browser is the primary target for every package they publish, not a side case: each published package must be loadable from a CDN (e.g. jsDelivr) and actually run in a page — "My main target is the browser for all these packages. So we should be able to load the published package from a CDN (e.g. jsdelivr) in the browser and run it." A design that works on disk/node but not from a CDN in a browser is wrong ("But then llvm will also not work in the browser"). Confidence: 0.85
- Prefers packages that install cleanly with no install-time lifecycle scripts: avoids `postinstall` (and similar) because such scripts are often blocked for security, and instead has the package's own code decompress/decrypt/decode lazily when it is actually used. Confidence: 0.75
- Cares about hard hosting size limits and wants them respected and verified: the whole published package under 150 MB (so jsDelivr will host it) and no single file over 100 MB (so GitHub will accept the push). Confidence: 0.7
- Chooses the payload format the target runtime can natively decode over a smaller one it cannot, even at a real size cost — e.g. per-file gzip inflated with `DecompressionStream` instead of one `.tar.xz`, because a browser cannot open xz and would have to inflate everything to reach one file. Confidence: 0.65
- When contributing to an existing project, follows that project's own contribution documentation and uses the established sibling module as the reference implementation (e.g. "See docs/.../adding-languages.mdx" and "Use `browser-nim` as a guide"), rather than inventing an approach. Confidence: 0.6
